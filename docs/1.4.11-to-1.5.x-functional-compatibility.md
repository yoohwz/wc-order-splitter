# 1.4.11 to 1.5.x functional compatibility

## Authority and scope

This document is the repository-owned functional compatibility contract for an in-place upgrade from the public Free `1.4.11` baseline to the 1.5.x hardened architecture.

The reproducible repository baseline is commit `e1d8aeb` (`wc-order-splitter.php` declares `Version: 1.4.11`). The 1.5.x comparison source for `WOS-COMPAT-001` is commit `9ac096c7ce3a216f9dad91d9a0bec160261f13ee`, tree `aaf21a3183f640c5bc16a00d83bab668a10212a4`. The canonical task and product decisions are in GitHub Issue #116.

Compatibility means preserving supported user outcomes through the current architecture. It does not authorize loading or restoring legacy mutation handlers.

## Classification vocabulary

- `PRESERVE_FUNCTIONAL_OUTCOME`: preserve the supported user-visible result through hardened 1.5.x code.
- `INTENTIONAL_1_5_X_CHANGE`: retain a reviewed 1.5.x behavior that deliberately differs from 1.4.11.
- `DEFERRED_COMPATIBILITY_WORK`: the mismatch is binding, but its runtime correction belongs to the named downstream task.
- `UNSAFE_LEGACY_IMPLEMENTATION_NOT_TO_PRESERVE`: do not restore the old mechanism even when a supported outcome must be preserved.

## Access contract

The complete plugin-level access equation is:

`administrator or shop_manager role` + `required WooCommerce capability on every participating order` + `workflow gate and hardened eligibility/authority` = usable workflow.

This applies to Split, Duplicate, Merge, Return and Bulk Return. Removing the legacy option does not relax nonces, Review/Confirm binding, per-order `edit_shop_order` / `delete_shop_order` checks, participant checks, status/settings checks, commercial preflight or code-owned workflow/strategy gates. A custom or lower-privilege role does not gain mutation authority merely by receiving WooCommerce order capabilities.

## Downstream boundary

`WOS-COMPAT-001` does not change Split status, shipping, coupon, fee, refund or nested-Split runtime behavior; Return/Bulk Return compatibility behavior; Merge commercial or financial support; Duplicate status; feature/strategy gates; versions; packaging; release or publication state. Those changes require their named downstream exact-head tasks and authority.

`WOS-COMPAT-002` owns only the Split functional outcomes recorded above. It preserves the hardened Review / Confirm / Execute, lock, journal, recovery, stock, historical-value and immediate-lineage architecture; it does not change Duplicate, Merge, Return, Bulk Return, workflow/strategy gates, versions, packaging, release or publication authority. Pre-WOS-COMPAT-002 durable Split journals retain their legacy `pending` child and source-only shipping semantics instead of being reinterpreted by current settings.

`WOS-COMPAT-003` owns only single-Return compatibility for corroborated public-Free `1.4.11` Split relationships. Compatibility is read-only until a confirmed operation starts, never forges current Split provenance, and executes through the current Return journal/replay/recovery system. It does not define Bulk Return `Eligible` / `Skipped` behavior, broaden refund/payment migration, change other workflow semantics or gates, or grant version, package, release or publication authority.

`WOS-COMPAT-004` owns only Bulk Return pre-existing row ineligibility. New v2 Review plans bind separate immutable disclosure and Eligible execution sets; Skipped rows receive no child operation UUID, confirmation, journal, lease or cursor position. Confirm requires at least one Eligible row and rejects either-direction classification drift. After Confirm, ordinary Return authority loss remains a fail-stop runtime outcome rather than a new Skip. Pre-v2 durable coordinators remain readable and replayable without migration. This does not broaden ordinary Return eligibility, restore the legacy direct loop, continue after runtime failure, change other workflow semantics or gates, or grant version, package, release or publication authority.

`WOS-COMPAT-005` owns only ordinary unpaid/non-refund Merge compatibility. Its versioned commercial policy retains target order-level context/status/charges, preserves source-only shipping/fee/coupon/context as retired-source history, and transfers exact source product-line outcomes by one server-frozen `coalesce` or `fresh_target_line` action per line. It preserves the existing gateway, Review / Confirm / Execute, pair lease, journal, recovery, stock guard, participation and non-force retirement authority. Pre-WOS-COMPAT-005 durable Merge journals retain their strict fresh-line/equal-context policy and replay without migration; stale transient Review/Confirm authority cannot create a new operation. Paid, transaction-bearing and refund-bearing Merge remains fail-closed for `WOS-COMPAT-006`. This task does not change other workflow semantics or gates and grants no version, package, release or publication authority.

`WOS-COMPAT-006` owns only the bounded Merge financial-history boundary. A source with `is_paid()`, paid date, transaction ID, refund amount or refund record remains unsupported and untouched because the existing source retirement path cannot move that audit authority. A financially historical non-terminal target may accept only source product lines whose exact persisted `total` and `total_tax` are each zero independently; such lines are always new target items and never coalesce into settled or refund-referenced target lines. Historical subtotal, subtotal-tax, classified metadata and `_reduced_stock` ownership remain exact, while target transaction/refund/status/payment authority, pre-existing items and charges, payable total, actual tax and tax rows remain unchanged. No payment/refund API, synthetic credit, settlement ledger or alternate retirement path is introduced. Pre-WOS-COMPAT-005 v1 and WOS-COMPAT-005 ordinary-commercial durable journals retain their exact frozen replay/recovery policies. Full cross-order settlement aggregation or refund migration requires a separately governed future architecture and is not part of `WOS-COMPAT-007` or `WOS-REL-001`. This task changes no workflow/strategy gate and grants no version, package, release or publication authority.
